## Fixed

### 1. A mail timeout killed the whole service

**Symptom.** `journalctl` showed the process exiting with `ETIMEOUT` and systemd
restarting it, twice, five minutes apart. The stack trace pointed at
`listOnTimeout` and looked nothing like a mail problem.

**Cause.** `ImapFlow` is an EventEmitter. A dropped connection arrives as an
`'error'` **event**, not a rejected promise — and in Node an `'error'` event
with no listener is an uncaught exception that ends the process. `fetchNew`'s
`try/catch` could never have caught it: the emit happens inside imapflow's own
socket-timeout timer, long after the awaited call has already returned. The
sequence was `mail: Command failed` → exactly five minutes of nothing → dead.

**Fix.** One `client.on("error", …)` listener, explicit connection/greeting/
socket timeouts, and `client.close()` in a `finally` so the socket is not left
alive to time out later. Verified by reproducing the crash and confirming the
same emit is survivable with the listener attached.

**Why it mattered more than it looks.** A crash during a wake loses that
check-in silently. systemd restarts, the log fills with a normal-looking boot,
and the family simply never hears anything.

### 2. A missed minute meant a missed check-in, silently

**Cause.** The scheduler fired only on an exact `hm === slot` string match. If
the process was restarting, crashed, or busy during that single minute, the
check-in never happened — and nothing logged, reported, or notified anyone.
Given the crash loop above, this was not hypothetical.

**Fix.** `server/src/schedule.js` — a slot stays due for a grace window
(`WAKE_GRACE_MINUTES`, default 90), the brief is told it is late and opens by
saying so, a failing slot backs off (5 min apart, 3 tries) instead of burning a
model call every 30 seconds, and after a long outage only the *latest* due slot
fires rather than a backlog of four. 11 tests in `schedule.test.js`; `npm test`.

A 07:00 brief at 07:12 is worth far more than no brief. A 07:00 brief at
lunchtime is not — hence the window rather than an unbounded catch-up.

### 3. A wake silently deleted anything that arrived while it was thinking

**Cause.** `runSlot` loaded state, spent 30–60 seconds in a model call, then
saved the copy it had loaded *before* the call. `ingest()` and the backgrounded
`answer()` both write state during that window. Their writes were overwritten.

**Effect.** A family message sent during a check-in, or a morning's mail, could
vanish with no error anywhere.

**Fix.** Reload immediately before writing, and only carry across what the wake
itself computed. The surrounding code already reloaded in three other places,
which is what made this one stand out as an oversight rather than a design.

### 4. `HEARTH_URL` was silently ignored — every push notification opened nothing

**Cause.** Line 3 of `server/.env` was a bare URL with no `HEARTH_URL=` prefix.
Every `.env` parser skips such a line without comment. `URL_BASE` therefore fell
back to `http://localhost:8787`, which is the tap-target embedded in every push
notification — and localhost on a phone is nothing.

Completely invisible from the server: sending the notification still succeeds.

**Fix.** Corrected in `.env` (previous file backed up to
`/root/hearth-env-backups/`, mode 600). `preflight` now fails on an unset or
localhost `HEARTH_URL`, and separately reports any `.env` line with no `=` by
line number — never by content.

### 5. Backup: the OFF case was the only silent one

`backup()` returned immediately when `BACKUP_GIT_REMOTE` was unset, so with no
remote configured nothing was copied anywhere and nothing ever said so. The
*failure* path warned the family in the check-in; the *never-configured* path —
strictly worse — said nothing at all.

**Fix.**
- Memory is now committed to a local git repo (`/opt/hearth-backup`) after every
  wake even with no remote. This is **not** a backup: same disk, same failure.
  What it buys is a rollback when the 22:00 review rewrites a layer badly, which
  is the likelier accident — and when a remote is finally set, every commit made
  up to that point pushes at once.
- The 22:00 check-in now says, once a day, that there is no off-machine copy.
- `git` runs with `GIT_TERMINAL_PROMPT=0`, so a stale token fails with a reason
  instead of hanging for the full 60-second timeout waiting on a username.
- `npm run backuptest` proves it end to end and names the actual cause on
  failure. `docs/backup.md` has the remaining steps.

Verified: the local repo holds 11 files, push subscriptions are correctly
stripped from the copied `state.json`, and no secret pattern appears anywhere
in it.

### 6. An empty calendar read as a quiet week

The configured feed is reachable and returns **zero events at any date** — not
zero in the window, zero in the file. The old code told the model "Calendar
reachable, nothing scheduled in the next 8 days", which invites Hearth to tell
someone their week is free while `rhythms.md` says otherwise. One confidently
wrong "you're free" costs more trust than a whole quiet day.

Now distinguished: an empty *feed* produces an explicit instruction not to treat
it as a free week and to work from `rhythms.md` instead. Confirmed reaching the
output — see the verification note at the bottom.

### 7. `.gitignore` did not cover `.env` backups

`server/.env` was ignored; `server/.env.bak.*` was not. Anyone editing the
secrets file the obvious way would have staged a copy of it. Now `.env.*` and
`server/.env.*` are ignored with `.env.example` explicitly re-included.

Also tightened to `600`: `server/.env`, and `.git/config` — which was `644`
while containing a GitHub PAT in its remote URL (see below).

## Diagnosed, deliberately not changed

### The 07:00 failure has a cause, and it is already gone

`Wake 07:00 FAILED: Could not resolve authentication method` — the Anthropic SDK
found no API key in the service environment at 07:00. The key is present now and
a live call succeeds, so the wake path itself was never broken.

The FAILED report is left in `state.json` on purpose. It is true history, it is
what the family saw, and `preflight` reports it until the day rolls over.
`preflight` would have caught this before the family was owed a brief.

### Nobody is subscribed to push — zero devices

`state.subs` is empty. Hearth's own notifications have **never reached anyone**;
the push Jeffery got at 07:05 was the harness's run-completion notification, not
a brief. With finding 4 also in play, a notification would not have opened
anything even if it had been delivered.

This is the adoption item, not a code bug, and it is now the single largest gap:
every wake fix above still ends in a notification nobody receives. Someone has
to add the app to a home screen and allow notifications — on iPhone, only a
Home-Screen app can, never a Safari tab. `preflight` warns while `subs` is empty.

### The family's schedule is not in the connected calendar

The feed is empty, and `rhythms.md` holds the real commitments (Abby's dance
Saturdays, soccer Tuesday/Thursday). Two readings, and I could not settle which
from the machine: either the ICS URL points at the wrong calendar of Jeffery's,
or the household genuinely keeps nothing in Google Calendar. **Worth one
question to Jeffery.** If it is the latter, standalone mode is the real mode
here and the calendar integration is decoration.

Not changed because both readings are plausible and guessing wrong means either
deleting a working config or leaving a broken one in place.

### `server/.env` defines three keys three times each

`GMAIL_USER`, `GMAIL_APP_PASSWORD` and `CALENDAR_ICS_URLS` each appear 3×. Last
one wins, and the values in effect are correct — mail and calendar both connect.

Left alone on purpose: I cannot confirm the duplicates are identical without
printing secrets, and silently rewriting someone's credentials file to tidy it
is a bad trade against zero current impact. `preflight` now names the duplicated
keys so it is visible rather than lurking. Worth a manual tidy, unhurried.

### The repo's `origin` remote embeds a GitHub PAT in plaintext

`.git/config` contained `https://x-access-token:github_pat_…@github.com/…`, and
the file was world-readable. Permissions are now `600`, but **the token itself
should be rotated**: it was readable by any process on the box, and it was
exposed in this session's output when the remote was listed.

Not rotated here — issuing and installing tokens is Jeffery's to do, and the
brief is explicit that nothing acts outward on anyone's behalf.

### Memory believes no scheduler exists. It does now.

`memory/daily/2026-08-22.md` records the abandoned trigger experiment and
concludes "Nothing is scheduled right now." That was true of the *claude.ai
trigger*. It is not true of the service, which owns its own clock and will wake
at 07:00, 12:00, 17:00 and 22:00 Eastern on its own.

A rendered 22:00 brief repeated the stale belief, telling Jeffery no morning
brief would arrive — while the service was sitting there scheduled to deliver
one. A system that contradicts itself about whether it is working is worse than
one that is plainly off.

**Not corrected by hand.** `memory/` is rewritten only by the 22:00 review; the
ops brief forbids editing it to make something look right, and that rule is
worth more than this one inconsistency. The review has everything it needs to
reconcile it — `CLAUDE.md` states the four slots. **If the stale claim is still
in memory on the 23rd, that is a genuine miss and belongs in `misses.md`.**
Check this first tomorrow.
