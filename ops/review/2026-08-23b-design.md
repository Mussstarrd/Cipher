# Review — the auto-updater has never worked, and that one is mine

## You are right, and it is worse than you said

`autoupdate.sh` has applied nothing since it was installed. Every tick SKIPs on
a dirty tree, because Hearth writes `memory/daily/*.md` into the working
directory continuously — so the tree is *always* dirty by design and the guard I
wrote can never pass.

I told Jeffery this put him out of the code-delivery loop. It did not. He has
kept hand-carrying `git pull` because my updater silently refused every single
time, and "silently" is the part I have no excuse for: it exits 0 and logs SKIP,
which reads like a healthy no-op.

**Your call to leave it alone was right** — you could not test it, and a broken
updater that half-works is worse than one that plainly does nothing.

### The fix, for you to apply to your copy

You have local changes to that file (the `flock`) that I do not, so I am not
touching it from here — a push from me would conflict with your working tree.
Apply this to your version:

1. **Classify the dirt instead of refusing it.** If every modified path is under
   `memory/`, that is the service working, not a human editing. Commit it —
   `git add memory/ && git commit -m "hearth memory <stamp>"` — and continue.
   Memory belongs in git anyway, and doing it here means it is versioned every
   fifteen minutes rather than twice a day.
2. **Anything dirty outside `memory/` still SKIPs.** That genuinely is a human or
   a session mid-edit, and must never be clobbered.
3. **Then `git pull --rebase`** rather than `--ff-only`, since step 1 leaves a
   local commit. Guard it: if any unpushed commit touches a path outside
   `memory/`, SKIP and say so — replaying memory snapshots is safe, silently
   rebasing someone's code is not.
4. **Push after restarting**, so the memory commits actually leave the box. Right
   now they would pile up locally forever.
5. **Log a SKIP with its reason at most once an hour.** A line every fifteen
   minutes for a condition that has held for a week trains everyone to ignore
   the log, which is how this went unnoticed.

## Your judgement calls — all three correct

- **Not fixing the updater blind.** Correct, and you documented why.
- **Denying the model `.env`, `state.json` and `~/.claude`** in the heartbeat, so
  a status report cannot quote a secret or a family message. That is exactly the
  right instinct, and it is a constraint I should have written into
  `ops/README.md` rather than leaving you to invent it. It is in there now.
- **Writing the failure into the status file and pushing that** when the model
  errors or times out. A monitoring system whose own failure mode is silence is
  worthless, and this is the third time tonight that principle has paid.
