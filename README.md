# Pocket Runner (POC)

Rhythm-based auto-run 2D platformer for Android, built in Godot 4.x / GDScript.
Boom-bap aesthetic: one swung 90 BPM track slot, head-nod groove. The character
auto-runs at a BPM-derived speed; you tap to jump and bounce off enemies in time
with the music. Placeholder rectangle art only — architecture is the point.

*(Repository: Cipher — Pocket Runner is the working title of the game POC.)*

## Requirements

- **Godot 4.3+ standard editor** (4.4.x recommended — needed for `targetSdk 36`
  gradle builds).
- **Android SDK** with platform **36** installed, plus **JDK 17**
  (Android Studio's bundled SDK/JDK works).
- A physical Android device with **USB debugging** enabled. Nothing is tuned for
  the desktop editor; desktop input (Space / left-click = tap) exists only for
  smoke-testing.

## One-click USB deploy

1. Open the project in the Godot editor once (this imports the WAVs and
   generates `.godot/`).
2. **Editor → Manage Export Templates…** → download the templates matching your
   editor version.
3. **Editor → Editor Settings → Export → Android**: set *Android SDK Path* and
   *Java SDK Path*. Leave the debug keystore fields as generated by Godot.
4. **Project → Install Android Build Template…** — required because the export
   preset uses a gradle build to target **API level 36**. This creates the
   git-ignored `android/` directory.
5. Plug in the device (`adb devices` should list it, authorized).
6. Click the **Android icon in the editor's top-right toolbar** (remote deploy).
   Godot builds the APK, installs it over USB, and launches it. That's the whole
   loop — edit, click, play on device.

The export preset (`export_presets.cfg`) is already configured: landscape
(sensor), immersive mode, `minSdk 24` / `targetSdk 36`, arm64-v8a, VIBRATE
permission, `*.json` files included in the export.

## Replacing the placeholder audio

The project ships with **silent** placeholder stems so it runs out of the box.
Drop in real files with the same names (then let the editor reimport):

```
tracks/demo/instrumental.wav    # the beat, minus the player-feedback drums
tracks/demo/player_drums.wav    # pre-rendered hit drums, same length/offset
tracks/demo/escalation.wav      # layered percussion for chain escalation
tracks/demo/demo.sidecar.json   # { bpm, offset_ms, swing_percent }
```

**WAV only.** MP3 encoder padding corrupts offsets and is deliberately
unsupported. All stems must be the same length and start at the same musical
position. Update the sidecar and `charts/demo.chart.json` (`bpm`, `offset_ms`,
`swing_percent`) to match the new track. The placeholders are 36 beats at
90 BPM (24.0 s); any length works as long as the chart matches.

## Architecture (the non-negotiables, and where they live)

- **Audio-time clock** — `autoload/song_clock.gd`. Raw position =
  `get_playback_position() + get_time_since_last_mix() - get_output_latency()`.
  Gameplay never reads that raw value directly: a smoothed clock advances by
  delta and blends ~5 % of the error per frame, snapping only past 100 ms
  (Android jitter filter). `current_beat` derives from smoothed time, BPM, and
  the first-downbeat offset. **No judgment or spawning uses frame delta.**
- **Unmute-based hit feedback** — `autoload/stems.gd`. `player_drums.wav` plays
  muted (-80 dB) in perfect sync at all times; a successful bounce unmutes it
  for `drums_unmute_beats`. No reactive one-shot tap sounds anywhere — instant
  physical feedback is haptic (`Input.vibrate_handheld`, stronger on success).
- **Beat-locked jumps** — `scripts/player.gd`. A jump is a fixed 1-beat sine
  arc interpolated over song beats. No gravity simulation. Run speed =
  `px_per_beat × BPM`, so N-beat spacing is constant on screen.
- **Levels are data** — `scripts/chart.gd`, `charts/demo.chart.json`. Schema:
  `{ bpm, offset_ms, swing_percent, audio_file, stems: { instrumental,
  player_drums, escalation[] }, events: [{ beat, type, nudge_ms, lane,
  duration_beats }] }` (last three default to 0). One generic runner scene
  (`scripts/runner.gd`) consumes any chart. Fixed BPM only — no tempo maps.
- **Difficulty = grid resolution** — easy/medium/hard anchor judgment and
  filter events to quarters/eighths/sixteenths by beat divisibility (swing
  shifts every off-16th, so hard placement is syncopated, not just denser).
  Window sizes live in `config/game_config.tres` (a `JudgmentConfig` resource,
  nothing hardcoded) and are clamped at runtime against the actual gap between
  neighbouring grid slots so adjacent windows never overlap.
- **Two-gate judgment** — `scripts/runner.gd`. Spatial gate: airborne (or a
  short landing grace) with feet inside the enemy's expanded head zone.
  Temporal gate: calibrated tap time inside the nearest grid slot's window.
  Inner window feeds the chain; outer only keeps you alive.
- **Sonic-style miss** — knockback flash, coins scatter and are briefly
  recollectable, chain resets, escalation stems mute. Death at zero coins is
  stubbed (refill + toast).
- **Chain escalation** — thresholds in config unmute escalation stems and
  drive background color shift + downbeat pulse.
- **Input** — single InputMap action `bounce` (touch via emulated mouse,
  Space/click on desktop). No raw touch reads in gameplay code.

## Screens

- **Main menu** → Play / Calibrate / Author Chart / difficulty cycle. Prompts
  for calibration on first launch.
- **Calibration** — synthesized metronome loop (generated at runtime, so it is
  clock-accurate like a real track) with visual pulse; 16 taps, outliers
  discarded, median offset stored in `user://settings.cfg` and applied to all
  temporal judgment.
- **Author mode** — track loops under a scrolling, swing-aware beat grid. Tap
  to place an enemy at the grid slot nearest the playhead (at the current grid
  resolution); DELETE mode removes the event nearest the tap; UNDO/SAVE
  buttons. Writes `user://charts/demo.chart.json`, which Play then prefers
  over the shipped chart.
- **Debug overlay** — DBG button (top right, any screen) or F3. Shows raw vs
  smoothed clock delta (jitter), reported output latency, last 10 judgment
  deltas in ms, current beat, chain, FPS. Use it on-device to decide whether
  deeper audio work (e.g. lower mix chunk sizes) is needed.

## Project layout

```
autoload/     song_clock.gd, stems.gd, settings.gd, debug_overlay.gd
config/       judgment_config.gd + game_config.tres (all tuning values)
scripts/      chart.gd, runner.gd, player.gd, enemy.gd, coin.gd,
              calibration.gd, author.gd, main_menu.gd, click_synth.gd
scenes/       minimal .tscn shells; all UI/world is built in code
charts/       demo.chart.json (shipped chart)
tracks/demo/  silent placeholder stems + sidecar JSON
```

## Known POC notes

- With a 1-beat jump, playable enemy spacing is 1 beat (air chain) or ≥ 2
  beats (land + jump between). The demo chart respects this; the authoring
  tool does not enforce it — tune by feel.
- Stems start via `play()` in the same frame, which is sync-accurate enough
  for a POC; sample-accurate scheduling is a post-POC refinement if the debug
  overlay shows drift.
