## Blocking findings

### B1. Cut with a start time past the end of the audio reports "Clip saved", marks the stage done, and writes an empty, unplayable clip

Spec §8.3: "bad timestamps ... a sentence in the UI". CLAUDE.md criterion 3: "never a
corrupted data file". Here the app produces a false success and an invalid output file,
and the failure surfaces three stages later as ffmpeg noise.

Reproduction (CLI, same via `POST /api/tracks/<id>/cut`):
```
ffmpeg -f lavfi -i "sine=frequency=440:duration=5" -c:a pcm_s16le "/tmp/qa-media/sine 5s.wav"
cd app; export RELEASELINE_DATA=/tmp/qa-cli/data
python3 -m releaseline new "Night Shift"
python3 -m releaseline cut 1 --start 0:10 --len 2 --src "/tmp/qa-media/sine 5s.wav"
```
Observed:
```
Clip saved: night-shift-clip.wav and night-shift-clip.mp3.    [exit 0]
```
- `clip/night-shift-clip.wav` is 78 bytes (WAV header only); `ffprobe` duration `N/A`.
- `clip/night-shift-clip.mp3` is 1089 bytes; `ffprobe`: "Failed to read frame size".
- DB `stages` row for `clip` is `state=done` with `wav`/`mp3` paths recorded; `assets` has
  both files. Start exactly at the end (`--start 5`) behaves the same.
- HTTP: `POST /api/tracks/1/cut {"start":"0:10","length":2,"src":".../sine 5s.wav"}` ->
  `200 {"ran": true, "message": "Clip saved: ..."}`.
- Downstream, with two shots in `video/`, `python3 -m releaseline assemble 1` fails with:
  `ffmpeg failed while trying to mux audio and write final video. It said: frame=    0
  fps=0.0 q=0.0 size=       0kB time=N/A bitrate=N/A speed=N/A` (four times). That tail is
  ffmpeg progress output, not the cause; a user cannot act on it.

Expected: a 400/exit-1 sentence such as "The track is 0:05 long; 0:10 is past the end.
Pick a start time inside the track." No files written, stage left as todo. ffprobe is
already located by `find_ffmpeg` and `probe_duration` exists in `media.py`, so the source
duration can be checked before cutting (and when ffprobe is missing, at least reject an
output whose probed duration is 0/None instead of marking the stage done).

## Non-blocking findings

Ordered roughly by how likely the owner is to hit them.

1. **Deleting `releaseline.db` while the server runs silently starts over.** With the
   server up, `rm data/releaseline.db`, then `GET /api/dashboard` -> 200 with zero tracks;
   `POST /api/tracks` creates a new track with id 1. `library/<slug>/` folders from the old
   DB remain on disk and a new track with the same title reuses the old folder (slug check
   is DB-only). Not corruption, but the Dashboard shows "No tracks yet" with no hint that
   `library/` is full of tracks. Suggest: when the DB is created fresh but `library/` has
   folders, say so on the Dashboard with the path.
2. **Concurrent creates with the same title: 7 of 20 parallel `POST /api/tracks
   {"title":"Concurrent"}` returned 500 `IntegrityError`.** `unique_slug` is computed
   outside the insert transaction (`tracks.create_track`), so two requests can pick the
   same slug. The UI disables the submit button while saving (`busy(submit, true)`), so a
   double-click is guarded; data stayed consistent (13 tracks, unique slugs, integrity ok).
   Fix by retrying on `IntegrityError` or computing the slug inside `BEGIN IMMEDIATE`.
3. **Wrong-type JSON fields reach code that assumes strings and produce 500
   "Something went wrong (AttributeError/ValueError/OverflowError/ProgrammingError)"**
   instead of a 400 sentence. The JSON shape is correct and tracebacks go to the terminal
   only, so §8.3 holds, but the message is the generic one. Cases: `prompts` with
   `preset: 7` or `["anime"]` or `setting: {}`; `prompts/choose` with `variant.shots: "x"`
   or `[1,2]` or `seed: {}`; `cut` with `src: {}`; `ffmpeg/test` with `path: {}`;
   `PUT /api/platforms` with `id: "abc"`; `GET /api/tracks/99999999999999999999999` and
   `PATCH .../drafts/99999999999999999999` (OverflowError); stage path of 10,000 chars
   (`OSError: File name too long` from `Path.is_file()` -- this one is reachable by pasting
   into the path field; wrap `is_file()` in try/except and return "File not found").
4. **Numbers and lists are coerced to text with `str()` rather than rejected.** `title:
   123` -> track "123"; `title: ["a"]` -> track "['a']"; `settings.artist: {"a":1}` ->
   artist "{'a': 1}"; `feedback.text: ["a"]` -> "['a']"; `seed: true` -> 1; `n: 3.5` -> 3.
   `n: 0` and `clip_len: 0` fall through `or` defaults and succeed with 4 variants / 30 s.
   The UI never sends these, so harmless, but the `_need`/`_clean_fields` layer could
   reject non-string scalars with one sentence.
5. **ffmpeg failure messages include raw stderr with memory addresses**, e.g.
   `[in#0 @ 0x55b8d65d6f80] Error opening input: Invalid data found when processing input`.
   README documents that the last ffmpeg lines are included, so this is by design, but
   stripping the `[... @ 0x...]` prefix and progress lines (`frame=... fps=...`) would make
   the sentence readable (see B1 for the worst case).
6. **CLI exit codes deviate from spec §5 for argument errors.** Spec/README: 0 ok, 1 "something
   you can fix", 2 unexpected. argparse errors (`new` with no title, `--seed abc`,
   `--aspect 4:3`, unknown subcommand, `serve --port abc`) exit 2 with a usage dump.
   Validation errors that reach the app (`--n 2`, `--preset claymation`, `--bpm fast`)
   correctly exit 1. Either document the argparse convention or map `SystemExit(2)` to 1.
7. **`python3 -m releaseline prompts ... | head -1` prints "Unexpected error
   (BrokenPipeError)" and exits 2.** Minor; catch `BrokenPipeError` in `main`.
8. **A posted URL of 50 KB and a feedback `screen` of 5,000 chars are accepted** (screen is
   truncated to 80 in `add_feedback`, URL is stored whole). Add a length cap for URLs.
9. **`stages.video.data.shots` accepts a non-list** (`{"shots":"x"}` stored as the string
   "x"); later `find_shots` iterates the characters and says "File not found: x". Reject
   non-lists.
10. **Backup caveat**: `assets.path` and stage paths are absolute. Copying `data/` to a new
    location and pointing `RELEASELINE_DATA` at it works (dashboard JSON identical, library
    listing correct), but the "recorded" assets will be flagged missing if the original
    location is gone. README says "put it back", which is accurate; one sentence about
    moving to a new machine would help.
11. **`test_without_ffmpeg_commands_are_shown` lives inside the ffmpeg-only
    `ExecutionTests` class**, so the one machine where it matters (no ffmpeg) skips it.
    `test_server.test_cut_and_assemble_without_ffmpeg_show_commands` covers the same path
    via a bogus `ffmpeg_path`, so coverage exists; move the test out of the skipped class.
12. **Malformed `Content-Length: abc` drops the connection** with a stdlib traceback in the
    terminal (`int()` in `_read_body` is outside the try). Browsers never send this.
13. **Stdlib `socketserver` prints tracebacks to the terminal** when a client disconnects
    mid-response (`ConnectionResetError` after a 414). Terminal noise only; the builder's
    "tracebacks for 500s go to the terminal only" note already covers the spirit of this.
14. One observation not reproduced: during the first attack run the 8612 test server died
    with no traceback in its log. Re-running the exact sequence (3 MB body via curl and
    urllib, then the full battery) twice on fresh servers: the server survived every time
    and returned `400 {"error": "That request is too large."}`. Another reviewer was running
    `pkill`-style cleanups on this machine at the same time; I attribute the death to that
    and do not count it against the app.

5. **Data integrity: PASS.** Full loop over HTTP with a 5 s sine WAV and two 2 s colour
