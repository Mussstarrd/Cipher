## Non-blocking findings

### N1. Reopen on a later stage jumps the page to an earlier undone stage
- **Where:** Track page, any done stage whose number is higher than the first undone stage.
- **Saw:** stage 1 to-do, stage 7 done. Click rail 7, press **Reopen** → stage 7 collapses
  and stage 1 expands (02-60). The thing you just reopened to edit is now folded. When all
  earlier stages are done, Reopen keeps the stage open, so this only bites out of order.
- **Expected:** the reopened stage stays expanded.
- **Fix:** in `act()` (app.js ~line 359) set `STAGE_OPEN[d.track.id] = s.key` when the new
  state is `todo`, `null` otherwise.

### N2. Settings: a stale red "ffmpeg was not found at '/nope/ffmpeg'" stays after the path is cleared
- **Where:** Settings → ffmpeg card (02-19).
- **Saw:** Test with a bogus path → red sentence (correct). Clear the box → the field shows
  the auto-detected placeholder `/usr/bin/ffmpeg (auto-detected)` but the red not-found
  sentence for the old path remains until the next Test or Save.
- **Fix:** clear the test result on `input` in the path field.

### N3. The "shorter clip" note lives only in a toast
- **Where:** Stage 3 after a cut that was clamped.
- **Saw:** the toast says the clip will be 0:20 long; after it fades the done view shows
  "Clip: <path>" with no length. The Length field does keep the clamped value (20), which
  is a hint, but not an explanation.
- **Fix:** add the duration to the "Clip:" line ("Clip (0:20): …"), from the probe already
  done in `check_clip_output`.

### N4. Stage 6 keeps the green "Final: …final.mp4" line above a red failure message
- **Where:** Stage 6 after a failed re-assemble when an earlier final exists (02-12c).
- **Saw:** "Final: …/night-shift-final.mp4  Copy path" in green directly above "ffmpeg
  failed while trying to normalize shot 3…". Both are true (the old file was preserved,
  which is the right behaviour), but a reader may think the failure produced that file.
- **Fix:** prefix the line with "Previous final:" when the last attempt failed, or move the
  error above the line.

### N5. ffmpeg failure text is still fairly raw
- **Saw:** "ffmpeg failed while trying to normalize shot 3. It said: [mov,mp4,m4a,3gp,3g2,mj2]
  moov atom not found [in#0] Error opening input: Invalid data found when processing input
  Error opening input file …/shot-03.mp4. Error opening input files: Invalid data found when
  processing input". It is a sentence with the file name and not a traceback, which meets
  the bar; the README describes exactly this. A one-line hint ("Usually the shot is not a
  playable video file.") before the quoted lines would make it friendlier.

### N6. Carry-overs from review 01, unchanged and still minor
- Duplicate titles silently become `night-shift-2/` (toast says so; fine).
- "Release anyway" uses the browser's native `confirm()`.
- The "chosen" badge and the "Chosen" button sit side by side on the chosen variant; one
  of the two would do.
- Pill reads "checking ffmpeg…" for the first paint (02-01); it resolves in under a second.

## What is good (do not break this)

- **Cold start is exactly as documented.** `cd app && python3 -m releaseline serve` prints
  the URL and data folder; `run.sh`/`run.bat` are one-liners around it; nothing to install.
  Zero page errors, zero 5xx responses across the whole run; the only console noise is
  Chromium logging the intended 400/404 responses from the validation probes.
- **Error copy is consistently a sentence, in place.** Missing path, bad time, past-the-end
  time, empty saves, bad URL, bad BPM, corrupt settings.json (names the file, "Fix it or
  delete it"), corrupt DB (names the file, "restore data/ from a backup"), deleted DB
  (amber notice, nothing destroyed), unreachable server ("Could not reach ReleaseLine. Is
  the server still running in the terminal?", 02-44), missing clip at assemble ("Cut the
  clip again in stage 3."). The footer and Feedback button survive every one of them.
- **Cut and Assemble are now safe.** No file is written for a bad start; a clamped cut is
  announced; a failed assemble leaves the previous final.mp4 untouched (verified by size)
  and the `.part`/`.work` temp files are cleaned up.
- **Stage 4 is a pleasure now**: Shuffle changes the seed and the prose, Use this marks the
  variant and updates Drafts without a page jump, and the "Chosen: … Press Generate (same
  seed)" line answers the question a first-timer would ask when returning.
- **Generators remain honest and specific**: "type beat" title rule fires on dark trap,
  YouTube tags 236/500 chars, distributor note carries the explicit flag; no screen,
  README, WALKTHROUGH or generated draft contains viral / guaranteed / grow your / blow up /
  passive income / promise outside the footer's "cannot predict or promise".
- **Phone width**: scrollWidth = clientWidth = 390 on every screen; rail wraps to three
  rows; the Upload stage is now usable with a thumb.
- **README and WALKTHROUGH match the screens.** Every quoted message in Troubleshooting
  ("0:45 is past the end of the file…", "ffmpeg produced an empty clip…", "The database
  was recreated…", "Could not reach…") is the real string; the walkthrough's new sentences
  about Reopen/Chosen/empty saves/phone upload blocks all describe what I saw.
- **CLI** mirrors the UI sentences; argparse errors now exit 1 with "Error: …".

## Time to complete the core loop as a first-timer

Scripted in-app time with files already on disk and ffmpeg present: **45 s** from "New
track" to "Released" (create, stages 1–3 including three refused cuts and two real cuts,
prompts + Use this, assemble, metadata, one posted URL, Release anyway). Reading each
stage's checklist and the prompt variants at a human pace I still estimate **8–10 minutes
in-app** for a first pass, excluding the work inside Suno, FL Studio, Kling and the upload
pages. Nothing in the loop required a guess this time; the only moment of hesitation I can
construct is N1 (Reopen jumping to an earlier stage), which does not occur in the normal
in-order flow.

## Embarrassment test

Demo-able without apology. The two things a peer would have noticed last round (a button
that says "Testing…" forever and a silent empty clip) are gone, and the recovery paths —
a shorter clip that says so, a failed assemble that keeps the old file, a lost database
that tells you your folders are still there — are the kind of detail that makes a tool
feel trustworthy.
