## Non-blocking findings

Ordered by how likely the owner is to hit them.

1. **A partially corrupt database (valid header, damaged pages) gives the generic 500
   instead of the database sentence with the path.** Repro: copy a good `data/`,
   overwrite bytes 4096–8192 of `releaseline.db` with random data, delete `-wal`/`-shm`,
   start the server. Startup succeeds (page 1 is intact so `connect()` and `executescript`
   pass); `GET /api/dashboard` and `GET /api/tracks` -> 500 `Something went wrong on the
   server (DatabaseError). Details are in the terminal where ReleaseLine is running.`
   with `sqlite3.DatabaseError: database disk image is malformed` in the terminal. CLI
   `list`/`new` -> exit 2 `Unexpected error (DatabaseError): database disk image is
   malformed`. Spec §4 asks for "a sentence and the path to check" when the database is
   unreadable, and §5 says exit 1 for things the user can fix (restore from backup).
   Nothing is corrupted further by the app. Fix: catch `sqlite3.DatabaseError` in
   `App.dispatch` and `__main__.main` and reuse the existing `The database at <path> could
   not be opened (<reason>) … restore data/ from a backup.` sentence (status 400 / exit 1).
   A fully garbage file still gives that sentence at startup (exit 1) and while running
   (400 on every DB endpoint, `/api/status` 200, recovery on restore without restart).
2. **Full disk gives the generic 500.** On a 400 KB tmpfs filled to 48 KB free, each
   `POST /api/tracks` -> 500 `Something went wrong on the server (OperationalError)` with
   `database or disk is full` tracebacks in the terminal (12 of them). Integrity `ok`, no
   partial track rows (transaction rolled back), small writes (feedback, settings) still
   succeeded, Dashboard still loaded, and after freeing space a restart worked with no
   notice. Two cosmetic leftovers: the 12 failed creates left empty `library/fill-N/`
   folders (made before the INSERT inside the transaction, same as the kill -9 case
   below), and the user sees no "disk is full" wording. Fix: map
   `sqlite3.OperationalError` containing "full" to a sentence naming the data folder.
3. **Settings accepts a `library_root` that is a file or an unwritable/nonexistent path.**
   `PUT /api/settings {"library_root": "/tmp/qa2-media/fake.wav"}` -> 200; from then on
   every track creation fails with `Could not create the library folder
   /tmp/qa2-media/fake.wav/<slug> (Not a directory). Check the library root in Settings.`
   The message points at the fix, so this is a sentence not a crash, but validating in
   `settings.validate` (is a directory, or can be created) would stop the owner saving a
   bad root. Same for `ffmpeg_path` pointing at a directory without ffmpeg or at a text
   file (accepted; the status pill then says not found / did not run, which is fine).
4. **Start within ~20 ms of the end is refused with the "empty clip" wording.** `start
   4.999` on the 5 s file -> 400 `ffmpeg produced an empty clip (166 bytes). Check that the
   source is a playable audio file and the start time is inside it. Nothing was saved.`
   The start *is* inside the file; the clamped length (0.001 s) is what produced nothing.
   `start 4.99` -> 960 bytes, same message; `4.9` -> 200 with a 0.1 s clip. Suggest: when
   the clamped length is below some floor (0.5 s?) say `Only 0.001 s of audio remain after
   0:04.999. Pick an earlier start.` Behaviour is safe (nothing saved, stage todo).
5. **Deeply nested JSON body and negative Content-Length drop the connection with a
   stdlib traceback in the terminal.** `POST /api/tracks` with `[`×50,000 `]`×50,000 ->
   no HTTP response (curl `000`), `RecursionError` from `json.loads` escapes `_read_body`
   (only `ValueError`/`UnicodeDecodeError` are caught). `Content-Length: -5` ->
   `ValueError: read length must be non-negative or -1` from `rfile.read(-5)`. Server
   survives both. Neither is sendable from the app's own UI. Fix: catch `RecursionError`
   alongside `ValueError`, and reject `length < 0`.
6. **`cut` with `start: 1e308` echoes a 300-digit number in the sentence** (`2777…
   is past the end of the file (0:05 long)`). Cap the formatted time or reject absurd
   values (`> 24 h`) with a short sentence. Cosmetic; it is a 400.
7. **Numbers that fall through `or` defaults are still silently replaced**: `prompts`
   with `n: 0`, `n: 3.5` (-> 3), `clip_len: 0` -> 200 using the default. Carried over
   from qa-01 finding 4; the UI never sends these.
8. **`prompts/choose` stores shot entries with non-string fields.** `shots: [{"n": {},
   "prompt": []}]` -> 200 and a shotlist draft reading `Shot {}: []`; `aspect: {}` /
   `duration: []` on the variant are stored as-is. `variant.prompt`, `label`, `negative`
   and the list shape *are* validated now. Validate `n` (int) and `prompt` (str) per shot.
9. **kill -9 mid-write leaves at most one orphan library folder.** 2,000 rapid creates,
   SIGKILL at 0.7 s: integrity `ok`, 173 tracks, all with 8 stages, 172 `kill-*` folders
   plus 1 folder with no row (mkdir ran inside the transaction before the INSERT committed).
   Documented in NOTES 17 (folder is reused by the next same-title track). Restart was
   clean, no notice. Acceptable; noting it for the record.
10. **Client-disconnect tracebacks in the terminal** (`BrokenPipeError`) after the server
    answers 400 to a 3 MB body or 431/414 to oversized headers. Terminal noise only, same
    as qa-01 finding 13.
11. **`HEAD /` and `OPTIONS /api/status` -> 501 with the stdlib HTML error page.** Browsers
    do not send these to this app; harmless.
12. **BrokenPipe on `| head`** (qa-01 finding 7) could not be reproduced this time (five
    attempts on `prompts`, `meta`, `list` with `head -c 1` all exited 0) and there is no
    `BrokenPipeError` handling in `__main__`; it is timing-dependent on output size vs the
    pipe buffer. Low priority; a two-line catch in `main` would close it.
