# UX review 01 — ReleaseLine v1

Reviewer: ux-reviewer (first contact with the app). Date: 2026-10-31.
Method: started the server from `app/README.md` alone (`python3 -m releaseline serve`,
with `RELEASELINE_DATA=/tmp/ux-review --port 8601 --no-browser`), drove it with headless
Chromium (Playwright) at 1280×720 and 390×844, probed the API and CLI by hand, and read
every screenshot. ffmpeg 6.1.1 is present on this machine; the no-ffmpeg path was exercised
by pointing Settings → ffmpeg path at a non-existent file. Test suite: 64 tests, OK, 17.7 s.
Scope: shelf-ready criteria 1, 2, 3, 5, 6 and the honesty rules.

## Verdict: FAIL

Two blocking defects, both small to fix. Everything else is in good shape; this is close.

## Blocking findings

### B1. "Cut clip" reports success and marks the stage done when the start time is past the end of the audio

- **Where:** Track page → stage 3 *Cut the 30-second clip*, with ffmpeg found. Also
  `POST /api/tracks/<id>/cut` and presumably `cut` on the CLI.
- **What I saw:** Master file is 70 s long. Entered start `5:00`, pressed **Cut clip**.
  Toast "Clip saved: night-shift-clip.wav and night-shift-clip.mp3.", stage 3 ticked green,
  stage 4 opened. On disk: `night-shift-clip.wav` is 78 bytes (a header, no audio) and
  `night-shift-clip.mp3` is 1 089 bytes and unreadable (`ffprobe`: "Failed to read frame
  size"). The Assets list shows both as present. Nothing warns. Assemble would then mux a
  silent/empty clip under the video.
- **What I expected:** A sentence under the Start field: "5:00 is past the end of the file
  (it is 1:10 long). Pick an earlier start." Nothing written, stage left as to-do.
  CLAUDE.md criterion 3: never a corrupted data file.
- **Suggested fix:** ffprobe is already detected (`ffmpeg.ffprobe` in `/api/status`).
  Before cutting, read the source duration with `ffprobe -show_entries format=duration`
  and reject `start >= duration` (and warn when `start + length > duration`). As a
  belt-and-braces check after any ffmpeg run, treat an output under ~1 KB or with no
  decodable duration as a failure ("ffmpeg produced an empty clip…") and do not mark
  the stage done. Add a test for start-beyond-end.

### B2. Buttons get stuck on their busy label ("Cutting…", "Testing…", "Saving…") after the action finishes

- **Where:** `app.js` `busy()`: the label is only restored when `busy()` is called with a
  third argument, but every caller restores with `busy(btn, false)`. Visible on:
  - Stage 3 **Cut clip** after any bad time (`zz`, empty) → button reads "Cutting…", enabled,
    forever (screenshot 06). Without ffmpeg, **Show ffmpeg command** reads "Building…" after
    every press (screenshot 51).
  - Settings **Test** → reads "Testing…" after every press, success or failure (screenshot 21b).
  - Settings **Save settings** → reads "Saving…" after a validation error (screenshot 21b).
  - New track / Edit details **Create track** / **Save details** → "Saving…" after any server
    error (seen with a corrupt `settings.json`, screenshot 40b).
  - Stage 7 **Generate** → "Generating…" after a server error.
- **What I saw:** A stranger sees a primary button labelled "Cutting…" next to the error
  sentence, retypes the time, and has to press a button that claims to be mid-operation.
  In Settings the Test button looks hung after the very first click.
- **What I expected:** The label returns to "Cut clip" / "Test" / "Save settings" the
  moment the request finishes.
- **Suggested fix (one line):** in `busy()`, restore `btn.dataset.old` whenever `on` is
  false, regardless of `label`:
  `if (on) { if (label !== undefined) { btn.dataset.old = btn.textContent; btn.textContent = label; } } else if (btn.dataset.old) { btn.textContent = btn.dataset.old; delete btn.dataset.old; }`

## Non-blocking findings

### N1. Phone width: the Upload table squeezes the Posted URL box to about 40 px
- **Where:** Track page → stage 8 at 390 px (screenshot 35).
- **Saw:** three-column table; *Format reminders* takes most of the width, the URL input
  shows only "https://" and the Save button sits under it. It works, but pasting and
  checking a URL on a phone, which is exactly when the owner will do this (TikTok and
  Instagram are posted from the phone), is fiddly.
- **Expected:** one card per platform at phone width: name + link, reminders in small text,
  full-width URL box, Save.
- **Fix:** in the `@media (max-width: 600px)` block, make `.stage-body table, tbody, tr, td
  { display:block }` for the upload table (or render a list instead of a table below 600 px).

### N2. Metadata drafts are rendered twice on the track page
- **Where:** Track page with stage 7 open (screenshot 14, 15, 16).
- **Saw:** the ten editable boxes (Title 1–3, descriptions, hashtags, tags, distributor
  note) appear inside stage 7 and again, in a different order (Titles last), in the
  **Drafts** card below. Both are editable; an edit in one does not update the other
  until reload. On a phone this doubles an already long page.
- **Expected:** one place to edit each thing. Drafts could hold only the chosen prompt and
  shot list plus a one-line "Titles, descriptions and tags are edited in stage 7".
- **Fix:** filter metadata kinds out of the Drafts card, or render metadata only there
  and link to it from stage 7.

### N3. After "Use this" the variant list vanishes
- **Where:** Stage 4 (screenshot 10).
- **Saw:** pressing **Use this** re-renders the stage with no variants shown; the button
  now reads "Generate (same seed)"; the chosen prompt is at the very bottom of the page in
  Drafts. A first-timer does not know the four variants can be brought back.
- **Expected:** the variants stay on screen with the chosen one marked "chosen".
- **Fix:** after choose, re-run `gen(lastSeed)` instead of collapsing, or keep the stage
  output and add a badge.

### N4. Empty values are accepted as saves
- **Where:** Stage 1/2/6 path fields, stage 5 shot paths, stage 8 posted URL.
- **Saw:** pressing **Save path** with an empty box toasts "Path saved."; pressing **Save**
  on an empty posted URL toasts "Saved.".
- **Expected:** "Enter a path first." (or, if clearing is intended, "Path cleared.").

### N5. Suno link field shows a browser bubble, not the app's inline sentence
- **Where:** New track / Edit details, `Suno link` is `<input type="url">`.
- **Saw:** typing `suno.com/x` and submitting shows Chromium's native "Please enter a URL."
  tooltip and blocks the submit, so the app's own sentence ("Links start with http:// or
  https://.") and the BPM sentence never appear together. Native bubbles look different
  on every browser and vanish on blur.
- **Fix:** add `novalidate` to the form (the JS already validates), or use `type="text"`
  with `inputmode="url"`.

### N6. "ffmpeg was not found…" sentence appears twice in stage 3 without ffmpeg
- **Where:** Stage 3 after **Show ffmpeg command** (screenshot 51): once as the standing
  note under the button and again as the response message above the command.
- **Fix:** drop the response copy when the standing note is already shown.

### N7. Duplicate titles are created silently
- **Saw:** creating a second "Night Shift" quietly makes `night-shift-2/`. Reasonable, but
  the toast could say "Another track is already called Night Shift; folder night-shift-2/."

### N8. "Release anyway" uses the browser's native `confirm()` dialog
- Works, matches the spec ("asks for confirmation"), but it is the only non-app-styled
  element. Acceptable for v1; an in-page confirm would be consistent with the Feedback modal.

### N9. Python version is not checked
- README promises a sentence for "Python too old"; the code has no `sys.version_info`
  gate, so an old interpreter would show whatever syntax error comes first. Could not
  verify here (3.13 installed). A two-line check at the top of `__main__.py` would make
  the README true.

### N10. Minor copy/layout
- Dashboard card subtitle "no genre yet" is fine, but the artist shows only when set, so a
  card reads "DJ Test" with no genre and another "no genre yet": consistent enough, just
  noting.
- Long description textarea is capped at 10 rows and the text is cut mid-line; the resize
  handle is the only hint there is more.

## What is good (do not break this)

- **Cold start is exactly as documented.** `cd app && python3 -m releaseline serve` prints
  the URL and data folder; `run.sh` works from any cwd; the port-conflict message is a
  sentence that names the fix. No pip, no build, no CDN; the page loads with zero console
  errors and no failed requests.
- **Empty state** is a single sentence plus the one button that matters.
- **Every error I provoked was a sentence in place, never a trace:** missing file paths
  (stage 1, 2, 5), bad times (`zz`, blank, negative, zero length), bad BPM, bad URL,
  invalid JSON body, blank title, 5 000-char title, unknown route, unknown track id,
  corrupt `settings.json` (names the file and says "fix it or delete it"), deleted DB
  (recreated cleanly, empty dashboard), corrupt DB (names the file, suggests restoring
  `data/`). The footer and Feedback button survive all of these.
- **Validation copy is unusually good**: "'zz' is not a time. Use m:ss like 1:05, h:mm:ss,
  or plain seconds." "Give the track a title. Everything else is optional." The ffmpeg
  not-found sentence includes the install command per OS.
- **The stage rail** reads at a glance: numbered circles, green ticks, grey dash for
  skipped, blue for current; Mark done / Skip / Reopen all work and the next stage opens
  automatically. Checklist ticks persist.
- **Generators**: prompts are specific and genre-aware (hip-hop vocabulary picked up from
  "dark trap"; "menacing" mapped to a dark mood bank), shot lists keep subject/location
  constant and vary camera and moment, Shuffle changes the seed and the text, the same
  seed reproduces. Metadata: the "type beat" title rule fired correctly, YouTube tags were
  236/500 chars, the distributor note carries the explicit flag, and nothing anywhere
  claims plays, streams, growth or income.
- **ffmpeg path is honest both ways:** with ffmpeg, Cut produced a 30.0 s WAV + MP3 and
  Assemble produced a 1080×1920 H.264/AAC 30.0 s MP4 from two 3 s test shots (looped to the
  clip) in about 10 s; without ffmpeg, the exact commands appear with Copy buttons and a
  CapCut/DaVinci checklist, and the pill turns amber.
- **Copy buttons** flip to "Copied" for 1.5 s and the clipboard contains the right text;
  the fallback message exists for browsers that refuse.
- **Feedback** is reachable from every screen (including error screens), refuses an empty
  note with a sentence, saves to `data/feedback.md` with timestamp and screen, closes on
  Escape and on the backdrop.
- **Phone width:** no horizontal overflow on any screen (scrollWidth = 390 everywhere); the
  rail wraps, forms stack, the footer stacks.
- **Honesty:** the footer sentence is on every screen; no screen, README, WALKTHROUGH or
  generated draft contains "viral", "guaranteed", "grow your", "blow up", or "promise"
  outside the footer's "cannot … promise". `meta.py` even has a banned-word list.
- **README** covers requirements, run, test, walkthrough, ffmpeg install per OS, where
  data lives, backup, troubleshooting (and the messages quoted there match the real ones),
  uninstall. **WALKTHROUGH.md** matches the screens I saw; I found no claim it makes that
  the UI does not do.
- **CLI** mirrors the UI with the same sentences and the promised exit codes (1 for user
  errors, 2 for an unknown subcommand).

## Time to complete the core loop as a first-timer

Scripted in-app time, files already on disk, ffmpeg present: about 2.5 minutes from
"New track" to "released" (create 10 s, stages 1–3 incl. a real cut ~45 s, stages 4–8 incl.
a real assemble ~75 s). Reading each stage's checklist and the prompt variants the way a
human would, I estimate **8–10 minutes in-app** for a first pass, not counting the work
inside Suno, FL Studio, Kling and the upload pages, which the app rightly leaves to you.
Nothing in the loop required a guess; the only places I stalled were the stuck busy
labels (B2) and finding the chosen prompt after "Use this" (N3).

## Embarrassment test

With B1 and B2 fixed: demo-able without apology. The copy is calm and specific, nothing
oversells, and the no-ffmpeg path degrades gracefully. As it stands, a peer would notice the
"Testing…" button on the first Settings visit, and a silent empty clip is the kind of thing
that costs an afternoon.
